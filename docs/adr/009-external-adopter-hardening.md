# ADR-009: External-Adopter Hardening — Gate Bead-Context, Gate Configurability, Deferred Bead Status, Spawn-Path Robustness

**Status:** Accepted — 2026-07-28
**Deciders:** operator (jedarden), via Claude Code
**Tracking:** plan.md Phase 13; GitHub issues [#7](https://github.com/jedarden/NEEDLE/issues/7), [#8](https://github.com/jedarden/NEEDLE/issues/8), [#9](https://github.com/jedarden/NEEDLE/issues/9), [#10](https://github.com/jedarden/NEEDLE/issues/10), [#11](https://github.com/jedarden/NEEDLE/issues/11)

## Context

On 2026-07-28, GitHub user `jarvis-laboratories` filed five issues within the same 23-minute window, all sourced from the same production adoption: NEEDLE-rs + bead-forge 0.3.0 running against a ~900-bead monorepo migrated from bd/Dolt, alongside a legacy orchestrator during a phased cutover. All five cite the same head commit, `74356cd` (also this repo's `main` HEAD at the time of triage), and each includes a proposed fix the reporter says is already running as a local patch in their production fork.

Each was independently confirmed against source at `74356cd` before any fix was written:

1. **#7 — gate hooks get no bead context.** `CommandGate::validate` (`src/validation/mod.rs:240`) takes `_bead: &Bead` and never reads it; `run_command` (`src/validation/mod.rs:278-305`) builds its `Command` with no `.env()` calls at all. A gate command has no way to know which bead it is judging except by racily guessing from `br list --json` assignee state — broken with more than one worker in flight.
2. **#8 — outcome handler hard-codes a 50s timeout around gate execution.** `handle_with_cancellation` (`src/outcome/mod.rs:311-312`) wraps the entire `handle()` call — which runs validation gates via `handle_success` → `gate.run(bead).await?` (`src/outcome/mod.rs:391-392`) — in a fixed `tokio::time::timeout(Duration::from_secs(50), ...)` with no config path to change it. A gate running a real verification workload (container test suite, secret scan, fresh-model diff verifier) needs minutes, not seconds.
3. **#9 — gate command stderr is truncated at a fixed 4096 bytes.** `CommandGate::MAX_OUTPUT_BYTES` (`src/validation/mod.rs:236`) is a `const`, applied unconditionally in `run_command`'s failure path (`src/validation/mod.rs:290-291`). When a gate vetoes, the truncated stderr is the entire diagnostic surfaced to the operator — test-suite tails and verifier rationales routinely exceed 4KB.
4. **#10 — `BeadStatus` rejects bead-forge's `deferred` status.** `BeadStatus` (`src/types/mod.rs:93-111`) already carries a `#[serde(alias = "completed")]` on `Done` and a bare `Closed` variant to absorb known bf/br status-string variance, but has no `deferred` handling at all. `bf list --json` emitting `"status":"deferred"` fails deserialization for that record — not the whole call, but the affected bead silently disappears from every strand and from `needle supervise`'s view of the queue. The reporter's store had 31 such beads (93 parse-error lines across a full-store probe), caught only because a cutover rehearsal diffed store counts against what workers could see.
5. **#11 — `supervise` spawns workers via a hardcoded PATH lookup.** `Supervisor::spawn_worker` (`src/supervisor/mod.rs:339`) builds its child command with `std::process::Command::new("needle")` (`src/supervisor/mod.rs:408`) — resolved from `$PATH` at spawn time, with no fallback to the running binary's own path. In the reporter's migration, a different legacy tool happened to occupy the name `needle` on `$PATH`; `supervise` believed it was spawning workers (cap=3, 5 ready beads) while worker heartbeats stayed at 0 for 60 seconds, because it was silently invoking the wrong binary.

All five share a root shape: NEEDLE's extension points (gates) and operational surfaces (spawn, status ingestion) were built and tested against NEEDLE's own defaults, and broke on first contact with a second, independent production user whose defaults differed — a longer-running gate, a differently-named binary, a bead store with an extra status value. None of the five requires a design change; each is a hardcoded constant or an unhandled variant becoming configurable or accepted.

## Decision

Fix all five as reported, following each issue's own suggested fix (already validated as a local patch in the reporter's production fork):

1. **#7:** Export `NEEDLE_BEAD_ID` and `NEEDLE_WORKSPACE` into the gate command's environment in `CommandGate::run_command`. `CommandGate::validate` already receives `bead: &Bead`; thread `bead.id` and `workspace` through to the `Command` via `.env(...)` instead of discarding them.
2. **#8:** Add `validation.outcome_timeout_seconds` to `Config` (new `ValidationConfig` section), default `50` to preserve current behavior, and use it as the `handle_with_cancellation` timeout duration instead of the hardcoded constant.
3. **#9:** Add `validation.stderr_cap_bytes` to the same `ValidationConfig` section, default `4096`, and thread it into `CommandGate` (constructed with the configured cap) instead of the `MAX_OUTPUT_BYTES` const. Pairs naturally with #8 — both are the same gate-configurability gap, both land in the same `ValidationConfig` struct.
4. **#10:** Add a `Deferred` variant to `BeadStatus` with `#[serde(alias = "deferred")]` — actually the canonical spelling already matches `snake_case` rename, so `Deferred` deserializes from `"deferred"` without an explicit alias; it is added purely alongside the existing `Done`/`Closed` variants, mirroring their doc-comment convention. `is_done()` and `Display` are extended so the match stays exhaustive: a deferred bead is explicitly *not* done, distinct from `Blocked` (blocked-by-dependency vs. deliberately-postponed are different states worth keeping separate now that both deserialize successfully).
5. **#11:** Resolve the worker spawn binary via `std::env::current_exe()` by default (the supervisor and worker are the same binary, so this is always correct absent an override), with an optional `worker.worker_binary_path` config override for cases where the running binary's path is deliberately not what should be spawned (e.g. a wrapper script). Log the resolved path once at supervisor startup so an operator can see at a glance what will actually be spawned, rather than discovering a mismatch only via stalled heartbeats.

None of the five changes default behavior for an existing NEEDLE deployment: #8/#9 preserve today's constants as defaults; #10 only accepts a previously-rejected value, it does not change handling of any value that previously deserialized; #11 changes *how* the binary path is resolved but resolves to the same binary in the normal case (supervisor and worker sharing one binary on `$PATH`); #7 only adds new environment variables, it does not remove or change any existing gate behavior.

## Alternatives Considered

- **#8/#9 as two separate config sections** (e.g. `outcome.timeout_seconds`, `validation.stderr_cap_bytes` in different structs) — rejected in favor of one `ValidationConfig` section, since both are configurability gaps in the same gate-execution path and the reporter's own production patch already groups them under `validation.*`.
- **#10: treat `deferred` as an alias for `Blocked`** instead of a new variant — rejected. Collapsing them would make `is_done()`/strand-visibility behavior for deferred beads inherit blocked-bead semantics with no evidence that's correct, and would foreclose deferred-specific handling later. A new variant with today's `is_done() == false` (same externally-visible behavior as any other non-terminal status) is the smallest correct fix; strand-level treatment of deferred beads (e.g. exclusion from ready-queue selection) is out of scope for this ADR and not something either issue asked for.
- **#11: fail spawn loudly if `needle` resolves to an unexpected binary** (e.g. hash-check against `current_exe()`) — rejected as a first pass; more invasive than the reporter's own patch and not what was requested. `current_exe()`-by-default plus a startup log line gives an operator a visible signal without adding a new failure mode.

## Consequences

- Gate authors can now write bead-aware gates (resolve the bead's own acceptance criteria, tag commits, write labels back) without racing other workers for bead identity — closes the stated goal of gates as an independent-verification extension point ("don't let the agent grade its own homework").
- Gates with real verification workloads (container suites, secret scanners, fresh-model diff verifiers) are no longer capped at whatever fits in 50 seconds and 4KB of stderr; both caps are now per-deployment tunable via `.needle.yaml` / global config.
- A bead-forge store containing `deferred` beads no longer loses them silently from strand/supervise visibility; the previously-affected beads (31 in the reporter's store) become visible again immediately upon upgrade, with no store migration needed since this is purely a deserialization fix.
- `needle supervise` can no longer be silently defeated by another binary sharing the name `needle` on `$PATH` — the common case (supervisor and workers built from the same binary) is unaffected, since `current_exe()` resolves to the same install either way.
- Adds one new config section (`validation`) and one new field on `WorkerConfig` (`worker_binary_path`); neither is workspace-overridable via `.needle.yaml`, consistent with the existing `NON_OVERRIDABLE_KEYS` treatment of `worker`/`health`/`limits`/`telemetry` (fleet-operational settings, not per-workspace ones).
