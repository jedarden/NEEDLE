# ADR-006: Bead Lifecycle Reliability — Test Isolation, Failure Quarantine, and Liveness-Independent Reclamation

**Status:** Proposed — 2026-07-21
**Deciders:** operator (jedarden), via Claude Code
**Tracking:** plan.md Phase 10

## Context

Found during a plan.md maturity review triggered by a 2026-07-21 lab fleet audit that asked "what's needed to get the fleet back up and running productively." The fleet was not resource-starved (load 3.0/12 cores, 42G RAM free) — it was **data-quality-starved**: real ready work was hidden behind phantom bead claims, and three independent, compounding defects were found in the same pass, all rooted in the same underlying weakness — NEEDLE has no reliable way to notice and correct a bead that is stuck in a state it should not be able to stay in indefinitely.

**1. NEEDLE's own test suite contaminates real repos.** Most of `tests/e2e/` and the Rust integration suite are properly isolated (`tests/e2e/lib/workspace.sh:33-46` uses `mktemp -d` + `export HOME="$FAKE_HOME"`; most Rust tests construct strands directly against `PathBuf::from("/tmp")`). But `dead_worker_cleanup_integration` (`tests/integration_tests.rs:1997-2096`) spawns the real compiled binary (`Command::new(CARGO_BIN_EXE_needle).arg("worker").arg("--once")...`) without overriding `HOME` and without disabling Explore. `ExploreConfig::default_enabled()` defaults `true` (`src/config/mod.rs:435-437`) and `ExploreConfig::default_workspace_root()` resolves to the real `$HOME` (`src/config/mod.rs:439-441`) — inherited straight from the test process. `CliOverrides` (`src/config/mod.rs:1858-1863`) has fields for `workspace`, `worker_name`, `agent_binary`, `max_workers`, but nothing to scope `explore.workspace_root` for a test run. This is the same shape of bug that, on 2026-07-20, left ~284 phantom `in_progress`/stale-assigned beads across ~22 real repos under `/home/coding` (fixture identifiers like `crash-agent-test-worker`, `missing-agent-test-worker`), confirmed via timestamp to be a single test run that walked real filesystem paths instead of an isolated fixture. The specific fixture IDs from that incident are gone from the current tree, but the mechanism that produced them — a real-binary test with no `HOME`/Explore isolation — is still present and will reproduce it on the next run that happens to reach this test path with a populated real home directory.

**2. No failure circuit-breaker.** A bead too large to finish in one agent turn hits `error_max_turns`, gets released, gets re-claimed, and fails again — with no automatic stop. Historical cost: one WASM-ABI bead accumulated 310 failures in 24h on one worker (~$1.6/run, ~$500 total), never auto-quarantined. Reviewed the actual mitigation surface:
   - `force_failure_threshold` (`src/config/mod.rs:490-496`, default `0` = disabled) only gates whether *mitosis re-fires* — it doesn't quarantine anything.
   - When mitosis judges a bead `NotSplittable` (the WASM-ABI case: genuinely atomic, just too big), `src/worker/mod.rs:2097-2100` logs and falls through to normal failure handling — no status change, no label, no alert.
   - `handle_failure` (`src/outcome/mod.rs:616-654,812-901`) unconditionally releases the bead and increments a `failure-count:N` label, **regardless of N**. There is no ceiling.
   - Pluck's `split_after_failures` (`src/strand/pluck.rs:476-518`, default 3) only forces a "please split this" prompt on the next dispatch — it still re-dispatches the agent every time; it does not block or quarantine.
   - Splice (added post-ADR-002, `src/strand/splice.rs:559-639,977-1022`) does implement a real circuit-breaker, but for a *different* pattern: `detect_completion_without_resolution` fires on repeated `bead.orphaned` events (mend reclaiming a stale claim after the agent silently died mid-task), not on `bead.released` (a worker's own clean release after `Outcome::Failure`). A bead that self-releases via `handle_failure` on every attempt never emits `bead.orphaned` — dispatch "completes" each time (with exit code 1), so Splice's other two detectors (`ClaimChurn`, gated on `bead.claim.race_lost`; and `LogRunaway`/`StatePingPong`, both gated on *absence* of `agent.completed`) are also blind to it, since `agent.completed` is present every time.
   - ADR-002 already names this precisely: its own Context states the fix "does not by itself prevent all forms of worker rabbit-holing (that's the broader failure-circuit-breaker problem tracked elsewhere)" (`docs/adr/002-pluck-telemetry-isolation-and-process-tracking.md:31`) — but no ADR or plan.md phase has ever picked it up. The 310-failure scenario is structurally still possible today.

**3. Mend is fleet-liveness-gated, and the fleet's own auto-scaler makes this a deadlock, not just a delay.** Mend (Strand 2) is only entered when Strand 1 (Pluck) finds no immediately claimable bead (`docs/plan/plan.md:1110-1132`) — it's a step inside a live worker's own waterfall loop, not a background daemon. `cleanup_orphaned_in_progress` (`src/strand/mend.rs:49-120`) — the only stale-claim reclamation function in the codebase — is called exclusively from `MendStrand`/`ExploreStrand` (`src/strand/mod.rs:67`, `src/strand/explore.rs:406`). `needle supervise`'s `tick()` (`src/supervisor/mod.rs:262-331`), the fleet's independent, dispatch-decoupled daemon, never calls it — and worse, `tick()` only spawns a new worker when `ready_beads` is non-empty (lines 306-309). Stale `in_progress`/stale-assigned-`Open` claims are *exactly* what suppress the ready queue, so a fleet that goes fully idle while holding only stale claims can never trigger a new worker spawn (nothing looks ready), which means mend never runs, which means the stale claims never clear, which means the ready queue stays suppressed — a closed loop with no external kick. `needle doctor --repair` (`src/cli/mod.rs:3511-3620`) checks config, JSONL/SQLite integrity, lock files, registry, heartbeats, and disk space — a repo-wide grep confirms zero `InProgress`/stale-claim reclamation logic anywhere in it. One historical instance: three beads stuck `in_progress` for ~12 days because their assigned worker had died with no other worker alive to trigger a waterfall pass.

**4. The reclamation NEEDLE already promised itself was never built.** ADR-001 named the specific sub-case of (3) that matters most in practice: an `Open` bead with a stale (non-empty but dead) assignee is functionally unclaimable forever, because `claim()` itself CAS-rejects `Open`+assignee-present beads (`src/claim/mod.rs:157`, "stale assignee") and both `pluck.rs:407-426` and `explore.rs:392,426` correctly exclude them from candidates on the same basis — that part of the filtering is not a bug, since claiming would fail anyway. ADR-001 (`docs/adr/001-explore-strand-hardening.md:16`) states plainly: "Stale assignees are permanent... nothing ever releases a stale assignee on an open bead," and plan.md Phase 5.2 (`docs/plan/plan.md:4012`) commits to "Mend releases stale assignees on open beads" as the fix. It never shipped: `cleanup_orphaned_in_progress`'s only branch explicitly requires `status == InProgress` (`src/strand/mend.rs:68`) and skips everything else. So the exact symptom the 2026-07-21 audit found — six roaming workers sitting `EXHAUSTED` indefinitely because the only candidates they ever discovered carried stale foreign assignees on `Open` beads — is not a new bug; it's a four-year-old promise (relatively speaking — Phase 5, 2026-07-13) that was scoped correctly in ADR-001 and then never implemented.

**External dependency risk, flagged not assumed:** whatever function ends up clearing a stale assignee on an `Open` bead has to call through `BeadStore` into the underlying `br`/`bf` CLI. As of the most recent check (bead-forge/`bf` 0.3.0), `bf update <id> --status open --assignee ""` was rejected ("Assignee cannot be empty or whitespace-only") and no `bf release` subcommand existed — this is a bead-forge-side gap, not fixable from NEEDLE's code, and needs re-verification against whatever `bf`/`br` version is current before 10.3 is implemented, since it may already have shipped a fix independently.

## Decision

1. **10.1 — Isolate `dead_worker_cleanup_integration` (and audit the rest of the real-binary test suite for the same gap).** The test must run with an overridden `HOME` pointed at a `tempdir`, and must either disable Explore outright (`explore.enabled: false` in the test's config) or scope `explore.workspace_root` to the tempdir. Add an `explore_workspace_root` field to `CliOverrides` if no config-file-based override is practical for a `Command::new()`-spawned subprocess. Establish this as a documented, enforced policy (CLAUDE.md Testing section): any test that spawns the compiled `needle` binary as a real subprocess must isolate `$HOME` and Explore's scan root, full stop — this is the second time this exact mechanism has caused real contamination.
2. **10.2 — A real failure circuit-breaker.** After K consecutive failures on a bead (config `outcome.quarantine_after_failures`, default matching or slightly above Pluck's existing `split_after_failures` default of 3 — e.g. 5, so mitosis gets a fair chance to split first), `handle_failure` sets `status: blocked`, adds a `cycling` label (distinct from the existing `deferred`/`human` labels so an operator can query specifically for this), and emits a `bead.quarantined` telemetry event (new Knot-strand alert class). This also closes the mitosis `NotSplittable` gap (Context point 2, second bullet) — a `NotSplittable` verdict should count toward the same failure ceiling rather than silently falling through. Quarantine, not auto-split — auto-splitting via mitosis on a threshold is a larger, separately-decidable follow-on, not required to close this gap.
3. **10.3 — Extend reclamation to stale-assigneed `Open` beads.** Add a sibling function to `cleanup_orphaned_in_progress` (or extend it) that releases the assignee on any `Open` bead whose assignee has no live heartbeat/registry entry, using the same staleness definition Mend already applies to `in_progress` claims (heartbeat TTL + dead-PID check). This is the Phase 5.2 fix, actually implemented. **Before implementation, re-verify the `bf update --assignee ""` behavior against the current `bf`/`br` version** — if still rejected, either file/confirm the upstream fix or have NEEDLE's `BeadStore::release()` implementation use whatever the current CLI's sanctioned clear-assignee mechanism is (do not work around it by touching `.beads/issues.jsonl` directly — see this repo's own convention against direct JSONL edits).
4. **10.4 — Decouple reclamation from worker liveness.** `needle supervise`'s `tick()` must call a mend-equivalent reclamation pass on every tick, **unconditionally**, before (not gated by) its `ready_beads`-non-empty check — breaking the deadlock in Context point 3, since reclaiming stale claims is a precondition for the ready queue becoming non-empty in the first place, not a consequence of it. As a second, independent path (useful for hosts not running `needle supervise` at all), add stale in-progress/stale-assignee reclamation to `needle doctor --repair`, so an operator (or a cron-style external trigger) has a standalone command that doesn't require any worker or supervisor to be alive.
5. **Ship 10.2-10.4 through the existing release path**: version bump, needle-ci (fmt + clippy + test on iad-ci), GitHub Release, staged canary rollout (`:testing` → `:stable`) — per plan.md's established Deployment convention (§6.8/§7.3/§8.5/§9.5). 10.1 is a test-only change and does not require a fleet rollout.

## Consequences

- Closes three independently-discovered, compounding gaps with one coherent phase, matching how Phase 6 bundled multiple sub-findings from a single incident review (ARMOR, ADR-002) rather than splitting them into unrelated ADRs.
- 10.2's quarantine label (`cycling`) needs its own operator-facing surfacing — `needle status`/`needle logs` should make quarantined beads easy to find, otherwise this just becomes a second kind of silent stuck state instead of a visible one. Not fully scoped here; flagged as a testing/UX requirement in Phase 10's Changes.
- 10.4's "reclaim before checking ready_beads" ordering change to `tick()` is a behavior change to the supervisor's own cadence — worth confirming it doesn't introduce a new tight loop (reclaim finds nothing → still no ready beads → tick again immediately) by keeping the existing backoff/interval between ticks unchanged; only the *order* of operations within one tick changes, not the tick frequency.
- 10.3 has a real external dependency (bf/br CLI behavior) that is outside this repo's control — implementation should not proceed until that's re-verified, to avoid landing code against an assumption that's already stale by the time it ships.
- Does not address 10.2's harder follow-on (auto-split via mitosis instead of quarantine-and-wait-for-a-human） — quarantine is the safe MVP; a human or a future phase still has to look at `cycling`-labeled beads and decide.
