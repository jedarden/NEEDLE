# ADR-010: Supervisor Zombie-Child Reaping and Zombie-Aware Liveness Checks

**Status:** Accepted — 2026-07-29
**Deciders:** operator (jedarden), via Claude Code
**Tracking:** plan.md Phase 14; GitHub issue [#12](https://github.com/jedarden/NEEDLE/issues/12)

## Context

On 2026-07-28, GitHub user `jarvis-laboratories` — the same production adopter behind issues #7–#11 (ADR-009), running NEEDLE-rs + bead-forge on a ~900-bead monorepo migrated from bd/Dolt — filed #12: `Supervisor::spawn_worker` never reaps the worker processes it spawns, so exited workers accumulate as `<defunct>` zombies under `needle supervise` for as long as the supervisor process runs. The reporter observed **22 zombies after ~15 minutes** of a cutover soak test on pin `v0.2.12` / `fad0b50`.

Confirmed against source at current `main`:

1. **No wait/waitpid/try_wait anywhere in the spawn path.** `Supervisor::spawn_worker` (`src/supervisor/mod.rs:377-498`) builds a detached child (`setsid` via `pre_exec`, `process_group(0)`, null stdio) and calls `cmd.spawn()?` (`src/supervisor/mod.rs:488`) with the returned `std::process::Child` immediately dropped — it is never bound to a variable, so there is no way to later call `.wait()`/`.try_wait()` on it. `setsid`/`process_group` detach the child from the controlling terminal/session; they do **not** detach it from being a reapable child of the supervisor process for `wait()` purposes — the supervisor remains the process that must reap it. A grep of the whole crate (`waitpid|try_wait|SIGCHLD|\.wait()`) turns up reaping logic only in `dispatch/mod.rs`, `telemetry/mod.rs`, and `canary/mod.rs` — all for different child processes (agent dispatch, a telemetry subprocess, canary binary checks), none for supervisor-spawned workers. Rust does not reap a child on `Child::drop` — dropping the handle only closes NEEDLE's own reference to it, it has no effect on the kernel-level parent/child relationship.
2. **This is a live, demonstrated bug in the supervisor's own capacity accounting, not just an operational nuisance.** `Supervisor::tick()` (`src/supervisor/mod.rs:308-336`) filters registered workers by `is_pid_alive(w.pid)` (`src/registry/mod.rs:28`, `kill(pid, 0) == 0`) to compute `alive_count`, then gates new spawns on `alive_count >= self.config.max_workers` (`src/supervisor/mod.rs:335`). `kill(pid, 0)` succeeds for a zombie (state `Z`) exactly as it does for a genuinely running process — a zombie still holds a PID table entry, it just hasn't been reaped yet. So every unreaped worker zombie is counted as "alive" by the supervisor's own tick, artificially inflating `alive_count` and potentially blocking new worker spawns at exactly the moment real capacity exists. The reporter's issue explicitly connects the two: "unreaped supervise children contributed to false `max_workers` capacity and silent 'hung' supervise logs" on a host that also had a large unrelated zombie population from PID 1.
3. **Not exploitable/reachable from outside the reported scenario.** This only manifests under `needle supervise` (the multi-worker fleet supervisor), not `needle run` (single-worker mode, no child-spawning). It requires the supervisor process to stay up long enough, and workers to exit, for zombies to accumulate — exactly the reporter's long-lived-daemon soak scenario.

The reporter's own suggested fix (validated as a local patch already running in their fork) is a `waitpid(-1, WNOHANG)` sweep once per `tick()`, as a smaller change than re-architecting the detach model to double-fork + reparent to init.

## Decision

1. **Reap exited children once per supervisor tick.** Add a reap sweep at the top of `Supervisor::tick()` (`src/supervisor/mod.rs`), looping `libc::waitpid(-1, &mut status, libc::WNOHANG)` until it returns `0` (no more zombies ready to reap right now) or `-1` with `errno == ECHILD` (no children left at all). `waitpid(-1, ...)` reaps *any* direct child of the calling process; since `needle supervise` only ever spawns worker processes directly (gate commands, dispatch subprocesses, etc. are spawned by the *worker* process, a separate PID tree), this is safe and cannot race with unrelated `.wait()` calls elsewhere in the codebase (`dispatch`/`telemetry`/`canary`), which all run in different processes. This is the reporter's own suggested fix and the smaller change against the current detach-only (`setsid` + `process_group(0)`, no double-fork) spawn model.
2. **Harden `registry::is_pid_alive` against zombie state on Linux.** A zombie is not meaningfully "alive" for any of this function's callers (supervisor capacity accounting, dead-worker registry cleanup, `strand::mend`'s liveness check) — it has already exited and is just awaiting reaping. On Linux, additionally check `/proc/<pid>/stat`'s process-state field (the character after the second `)` in the `comm` field, robust to command names containing parentheses) and treat state `Z` as *not* alive, even though `kill(pid, 0)` still succeeds for it. Falls back to today's `kill(pid, 0)`-only behavior on non-Linux platforms (no `/proc` on macOS) and if `/proc/<pid>/stat` is unreadable for any reason (permissions, race with process exit) — never *more* strict than today's check, only *additionally* strict for the one case (`Z`) that today's check gets provably wrong.
3. **Do not touch `cli::is_pid_alive`.** `src/cli/mod.rs` has its own, simpler, duplicate `is_pid_alive` (`kill(pid, 0) == 0` with no errno handling) used for `needle status`/`needle cleanup` display and filtering — not for supervisor capacity gating. It has the same zombie blind spot in principle, but fixing it is not necessary to resolve #12 (the reported impact is specifically supervisor capacity accounting and zombie accumulation under `needle supervise`) and is out of scope for this ADR. Left as a known, smaller follow-up if `needle status`/`needle cleanup` output for zombies becomes its own complaint.

## Alternatives Considered

- **Double-fork + reparent to init**, so `needle supervise` never owns the worker as a direct child and zombies are reaped by PID 1 instead — rejected as a first pass. It is the more "correct" long-term detach model but a materially bigger change to the spawn path (an intermediate fork, exit, and re-exec dance) than the reporter's own validated patch, for a problem a per-tick `WNOHANG` sweep already fully solves at the current poll cadence.
- **Retain `Child` handles and `try_wait()` each tick** instead of a raw `waitpid(-1, ...)` sweep — a more idiomatic-Rust alternative the reporter also mentioned. Rejected in favor of the raw sweep: it would require threading a `Vec<std::process::Child>` (or a map keyed by worker id) through `Supervisor` state that does not exist today, purely to recover information (`waitpid(-1, ...)` giving "some child exited") that the raw sweep gets for free without new state, and — since `needle supervise` has no other reason to hold live child handles — offers no benefit over the sweep for this specific spawn model.
- **Fix `is_pid_alive` on all platforms** (e.g. via a `sysctl`-based state check on macOS) — rejected as out of scope. The reported symptom is Linux-specific (production host, `/proc`-based observation); this codebase already carries a Linux/macOS branch in `is_pid_alive`'s own errno handling (`#[cfg(target_os = "linux")]`/`#[cfg(target_os = "macos")]`), so adding a Linux-only zombie check is consistent with the existing platform-parity bar, not a new gap.

## Consequences

- `needle supervise` no longer leaks a zombie process-table entry per exited worker for the lifetime of the supervisor daemon — the primary reported symptom.
- Supervisor capacity accounting (`alive_count >= max_workers`) can no longer be fooled by an unreaped-but-exited worker into believing the fleet is at capacity when it is not — closes the "false capacity hang" the reporter connected to the zombie leak.
- No behavior change to a deployment with no zombies today: the reap sweep is a no-op when `waitpid(-1, WNOHANG)` immediately returns `ECHILD`/`0`, and the zombie check in `is_pid_alive` only changes the answer for the one state (`Z`) that was previously wrong.
- `strand::mend`'s liveness check (`src/strand/mend.rs:707`, also calls `registry::is_pid_alive`) inherits the same zombie-awareness fix for free, since it shares the function.
- Adds a `libc::waitpid` call to the supervisor tick's hot path (once per `poll_interval_secs`, default multi-second cadence) — negligible cost, bounded by the (small) number of actual zombies, not by anything proportional to fleet size.
