# ADR-012: Wire the Failure-Quarantine Circuit Breaker and Add Failure-Aware Pluck Ordering

**Status:** Accepted — 2026-07-30
**Deciders:** operator (jedarden), via Claude Code
**Tracking:** bf-2tow4 (BeadStore::block primitive), bf-5rp29 (quarantine wiring), bf-3milo (Pluck sort), bf-u3aca (tests)

## Context

Triggered by a live audit of the lab fleet (`100.81.129.38`, 15 pinned workers) after the operator noticed the fleet-wide "beads processed" counter (717) didn't square with actual git commit volume (~52 commits/24h across all 15 repos). Grepping each worker's `.stderr.log` for `outcome="failure"` vs `outcome="success"` found **six of fifteen workers with zero logged successes** despite each showing 47-52 "beads processed": `warden-p1` (570F/0S), `cprint-p1` (438F/0S), `pdftract-p1` (396F/0S), `zai-p1` (366F/0S), `acb-p1` (396F/0S), `gantry-p1` (396F/0S). Each had one dominant bead retried dozens to hundreds of times: `wd-1sk`×96 (warden), `bf-2inl`×73 (claude-print), `bf-677eo`×66 (pdftract), `bf-5ga`×61 (zai-proxy), `bf-3ekm`×66 (ai-code-battle), `bf-61ov`×66 (gantry-rs). The remaining nine workers had non-zero successes but still logged 5-10x more failures than successes, with their own worst offenders retried 118-198 times (`bf-172ww`×195 on NEEDLE itself, `bf-66pw`×198 on SEAM, `bf-2kdqol`×159 on commitgraph).

`wd-1sk` is the same bead named in ADR-011 as a trigger of the 2026-07-30/31 fleet collapses (mitosis-evaluation timeout leaking orphaned `claude` processes). ADR-011's process-group kill guard (commit `6b25ec6`) closes the *crash* consequence of a bead like this cycling forever, but does nothing about the cycling itself — a bead can now fail 96 times safely instead of leaking a process 96 times, which is strictly better but still 96 wasted agent turns (~$1.6/run per the historical bf-37n8 precedent) with nothing to show for it.

### The circuit breaker was scaffolded but never wired in

Investigating why `wd-1sk` and the others were never quarantined despite ADR-006 §10.2 (`docs/adr/006-bead-lifecycle-reliability.md`) proposing exactly this fix on 2026-07-21, found that **§10.2 had already been partially built, then abandoned mid-implementation**, on this exact commit (`6b25ec6`, the ADR-011 fix):

- `OutcomeConfig::quarantine_after_failures` (`src/config/mod.rs:1758-1782`, default 5) — present and correctly wired to config loading.
- `EventKind::BeadQuarantined` (`src/telemetry/mod.rs:226-230`, plus `Display`/`bead_id()`/redaction-list arms) — present and correct.
- `OutcomeHandler::quarantine_bead` (`src/outcome/mod.rs:1035-1107`, pre-fix) — present, but:
  1. Marked `#[expect(dead_code)]` and **never called from anywhere** (`grep -rn "quarantine_bead(" src/` matched only its own `async fn` line).
  2. Its own doc comment says "setting status=blocked and adding the 'cycling' label," but the body only did the label half — there is no `BeadStore` method that can set a bead's status to `Blocked` at all (the trait has `release`/`claim`/`reopen`, each hardcoded to a specific status via the underlying `br`/`bf update --status` CLI call, but nothing generic and nothing for `blocked`). The function could not have quarantined a bead even if something had called it.
  3. `handle_failure` (`src/outcome/mod.rs:660-698`, pre-fix) unconditionally released every failed bead back to `open` and incremented its `failure-count:N` label with no ceiling — exactly the "no failure circuit-breaker" gap ADR-006 and the historical bf-37n8 incident (310 failures/24h, ~$500) both describe, still fully present.
  4. Mitosis's `NotSplittable` verdict (`src/worker/mod.rs:2376-2379`) still fell straight through to a debug log with no action, per ADR-006's Context point 2 and the still-open GitHub issue #10 discussion.

This is a real instance of the class of gap this repo's own `docs/notes/self-modification-risks.md` and CLAUDE.md Testing policy exist to catch: code that type-checks, passes `clippy`, and even has a config knob and telemetry event ready to go, but was never actually connected to the path it was meant to guard. `#[expect(dead_code)]` suppressed the compiler's own warning about this.

### Sort order compounds the problem

`PluckStrand::sort_candidates` (`src/strand/pluck.rs:175-182`, pre-fix) sorts ready candidates by `(priority ASC, created_at ASC, id ASC)` — `failure_count` never enters the ordering, despite `extract_failure_count` (`pluck.rs:162-169`) already existing and being used by the split-trigger check two dozen lines later in the same file. A bead that has been failing for a while is, by construction, at least as old as the ready siblings behind it, so it sorts to slot 1 and gets re-selected first, every single cycle — the six zero-success workers above were not just failing to quarantine `wd-1sk`-class beads, they were failing to *even attempt* the other ready work sitting behind them in the same repo, because the poison bead always won the sort.

## Decision

1. **`BeadStore::block(&self, id: &BeadId) -> Result<()>`** (`src/bead_store/mod.rs`): new required trait method, implemented for `BrCliBeadStore`/`BfCliBeadStore` via `run_br`/`run_bf(["update", id, "--status", "blocked"])` (mirroring `release`'s existing `--status open` call), and as a trivial no-op or state-tracking stub (matching each mock's existing idiom) across every `#[cfg(test)]` `impl BeadStore for X` in the crate. Deliberately does not clear the assignee or return the bead to a claimable state — that asymmetry with `release` is the whole point.
2. **Finish `quarantine_bead`**: call the new `store.block(&bead.id)` (with the same 30s-timeout-non-fatal pattern every other `br`/`bf` call in this handler already uses) in addition to the existing `add_label(cycling)`, and drop `#[expect(dead_code)]` now that it has a real caller.
3. **Wire it into `handle_failure`**: after `increment_failure_count` returns the new count, if `quarantine_after_failures > 0` (0 = disabled, matching the existing convention on `force_failure_threshold`) and the new count has reached it, call `quarantine_bead` and return `BeadAction::Quarantined` (new variant, `src/types/mod.rs`) instead of `BeadAction::Released`. This single check point closes the `NotSplittable` fallthrough as a side effect — mitosis's post-failure split evaluation (`worker/mod.rs:2339-2419`) runs *after* `handle_failure` every cycle (see that block's own comment: "the bead has already been released and failure count incremented by the outcome handler"), so once the ceiling fires here, the bead is `Blocked` before mitosis would have had a chance to fall through on it again — no separate check needed in the `NotSplittable` arm itself.
4. **Failure-aware Pluck ordering**: change `sort_candidates`'s key to `(priority ASC, failure_count ASC, created_at ASC, id ASC)`, reusing `extract_failure_count`. This is a genuinely new decision, not part of ADR-006 §10.2 — it's a low-risk, purely-comparator mitigation that reduces wasted cycles *before* a bead reaches the quarantine threshold, by letting a worker route around a currently-struggling bead toward its healthier siblings instead of hammering the same one every cycle. It composes cleanly with the quarantine breaker: sort order only changes which bead is picked each cycle, not whether `handle_failure`'s ceiling check runs, so a bead that keeps getting picked (because nothing healthier is left) still quarantines at the same count regardless of queue position.
5. Quarantine, not auto-split, per ADR-006's original scoping — a `cycling`-labeled, `blocked` bead still needs a human (or a future phase) to look at it and decide. Not addressed here: ADR-006 §10.1 (test isolation), §10.3 (stale-assignee reclamation), §10.4 (supervisor-decoupled reclamation) remain open, tracked separately in ADR-006 / plan.md Phase 10.

## Alternatives Considered

- **Only fix the sort order, skip the quarantine wiring** — rejected: reshuffling delays the waste but does not bound it. A bead with no other ready siblings left in its repo (the common case for a *pinned* worker once its healthy backlog drains — exactly what six of fifteen lab workers hit) still gets picked every cycle regardless of sort key, so sort order alone converges back to the status quo once the repo's healthy work runs out.
- **Only fix the quarantine wiring, skip the sort order** — rejected as leaving real, avoidable waste on the table: a bead can still accumulate `quarantine_after_failures - 1` failures while sorting ahead of healthier same-priority work purely by virtue of being older, before finally quarantining. The sort fix is a few lines and directly addresses the "shuffling" the operator asked about.
- **Auto-split on quarantine instead of blocking** — rejected, unchanged from ADR-006's own reasoning: splitting requires a design for what a "child" of an already-atomic, NotSplittable-judged bead even means, and is explicitly deferred as later, harder work.
- **Lower `quarantine_after_failures` below `split_after_failures` (3)** — rejected: would quarantine before mitosis gets a chance to try splitting a genuinely-too-big bead, defeating the ordering ADR-006 already chose (5 > 3, "mitosis gets first crack").

## Consequences

- A bead that keeps failing now stops burning agent turns after `quarantine_after_failures` (default 5) consecutive failures, instead of the unbounded retry observed in production (up to 198 times on `bf-66pw`). Matches the historical bf-37n8 incident's fix recommendation directly.
- `needle status`/`needle logs` do not yet have a dedicated "show me `cycling`-labeled beads" view — ADR-006's Consequences section already flagged this as a follow-on UX gap, still true here, not addressed in this ADR.
- The sort change is behavior-visible: operators watching `needle status` / bead-claim order will see healthier beads dispatched ahead of struggling ones at the same priority, where previously age alone decided. Existing test `candidates_sorted_by_priority_then_created_at` (`pluck.rs`) is unaffected — its fixture beads carry no `failure-count` label, so the new key component is a no-op tie (0 == 0 == 0) and falls through to the original ordering unchanged.
- Two extra `br`/`bf update` calls happen on the cycle a bead crosses the threshold (the existing unconditional release-to-open, immediately followed by block-to-blocked) rather than restructuring `handle_failure` to skip the redundant release. Accepted as the lower-risk option — it does not touch the already-tested flush/release sequencing, at the cost of one harmless extra CLI round-trip on the (rare, threshold-crossing) unhappy path only.
- Does not touch ADR-006 §10.1/§10.3/§10.4 — those remain planned, tracked in ADR-006 and plan.md Phase 10.
