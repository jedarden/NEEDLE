# ADR-007: Deploy-Path Hardening — Hot-Reload Self-Healing and Spawn-Path Guardrails

**Status:** Proposed — 2026-07-21
**Deciders:** operator (jedarden), via Claude Code
**Tracking:** plan.md Phase 11

## Context

Found during a plan.md maturity review of NEEDLE's own deploy history. Two separate incidents, both involving the same underlying mechanism, neither addressed by ADR-005 (Phase 9), which solves a different problem in the same area (getting a *new* GitHub release into the `:testing` slot automatically — not making the existing hash-based hot-reload check resilient to how binaries actually get replaced on disk today).

NEEDLE's worker hot-reload (`check_hot_reload()`, `src/upgrade/mod.rs:360`, run every worker-loop cycle at a safe boundary) compares `file_hash(get_current_binary_path())` against `file_hash(~/.needle/bin/needle-stable)`. `get_current_binary_path()` (`src/upgrade/mod.rs:311-313`) does call `env::current_exe()` fresh each cycle — it is not cached or stale by construction. The problem is what happens when that fresh call resolves to a path Linux has already unlinked:

- **2026-04-30 (`cp` incident, ex44):** installing a new build via `cp NEEDLE/target/release/needle ~/.local/bin/needle` while 20 workers were running caused every one of them to detect a hash mismatch against the (now-different-content) spawn-path file and re-exec into `:stable` immediately — losing whatever the new build was intended to deliver and disrupting all 20 sessions at once. `cp` overwrites file *content* in place; every running worker's `env::current_exe()` still resolves to a valid, readable path, so the hash check works exactly as designed — it just wasn't the deploy the operator wanted, because the spawn path was written to directly instead of routing through `:testing`.
- **2026-07-20 (`mv` incident, v0.2.12 rollout):** `mv`-replacing the spawn-path binary (`~/.local/bin/needle`) instead of `cp`-ing over it was expected to avoid the previous incident's disruption. It produced a *worse*, silent failure: `mv` unlinks the old directory entry and creates a new one, so any process still holding the old inode open (every running worker) now has `/proc/self/exe` resolving to `"…/needle (deleted)"`. `file_hash()` (`src/upgrade/mod.rs:320-327`) does `fs::read()` on that literal string, which errors every time. `Worker::check_hot_reload()` (`src/worker/mod.rs:2413-2416`) catches that error with `tracing::warn!("hot-reload check failed, continuing")` and returns `Ok(())` — the worker carries on, but has now permanently lost the ability to ever hot-reload again, since the next cycle's `env::current_exe()` resolves to the same deleted path and errors the same way. No special-casing of a deleted/unlinked exe exists anywhere in `src/upgrade` or `src/canary` — confirmed by direct read, not inferred. Affected workers stay on the pre-rollout version until they exit naturally (idle timeout, crash, or manual stop); only freshly-launched workers pick up the new binary.

Both incidents share a root cause: **the sanctioned deploy path (`needle upgrade` → canary → promote to `:stable` → workers hot-reload from `:stable`) exists and works, but nothing prevents an operator from writing directly to the spawn-path binary instead, and the hot-reload check has no recovery behavior for the specific failure mode that direct-write produces.** Plan.md documents the correct procedure in prose ("Never overwrite a running binary in place... verify with `needle status`", `docs/plan/plan.md:4034`) — this is advisory only, not enforced by any code path, and evidently was not sufficient to prevent either incident from a careful operator.

Separately, and orthogonal to hot-reload: `perform_upgrade()` (`needle upgrade`'s implementation, `src/upgrade/mod.rs:216-308`) still `fs::rename`s a freshly-downloaded GitHub release directly over `env::current_exe()` (lines 280-281) with **zero canary validation** — the same unvalidated-overwrite shape as the incidents above, just invoked deliberately via a documented command instead of by accident via `cp`/`mv`. ADR-005's own Decision explicitly leaves `perform_upgrade()` unchanged (Decision #4: "`needle upgrade` / `perform_upgrade()` remains available unchanged") and its Alternative #1 acknowledges canary-validating it is "worth doing as a small independent hardening regardless... filed as a separate, smaller bead" — but no such bead or phase exists in this repo today. `needle upgrade` is, structurally, a third way to reproduce the same class of incident, just with better UX around it (a real command instead of a raw filesystem operation).

## Decision

1. **11.1 — Self-heal the deleted-inode case in hot-reload, instead of erroring silently forever.** When `get_current_binary_path()`'s resolved path indicates a deleted/unlinked exe (Linux appends `" (deleted)"` to `/proc/self/exe`'s readlink target; alternatively detect via `fs::read()`'s `ErrorKind::NotFound` on that specific path), treat this as an **unconditional signal to re-exec against `needle-stable` immediately** — not a warning to log and continue past. The reasoning: a worker whose own spawn-path binary has been unlinked is, by definition, running on a file that no longer exists on disk (an orphaned inode, kept alive only by the open file handle) — there is no future in which continuing to run it is better than reloading, and no legitimate scenario where the correct response is "keep running the deleted version forever." This turns the exact 2026-07-20 failure mode into a one-cycle hot-reload instead of a permanent stall, without requiring the operator to have done anything differently.
2. **11.2 — Route `needle upgrade` through the existing `:testing`→canary→`:stable` pipeline instead of a raw overwrite.** `perform_upgrade()` should write the downloaded release to `~/.needle/bin/needle-testing` (reusing 9.1's target path from Phase 9, if landed first — otherwise this phase adds the equivalent standalone) and invoke the existing canary validation before promotion, rather than `fs::rename`-ing directly over `env::current_exe()`. This closes ADR-005's explicitly deferred item rather than leaving it as an unfiled "someday." `needle upgrade`'s UX (a single command an operator runs) is unchanged; what changes is that it no longer bypasses validation just because it was invoked manually.
3. **11.3 — A guardrail that makes unsanctioned spawn-path writes visible, since they can't be fully prevented.** Add a check (in `needle doctor`, and/or a startup check each worker already performs during BOOTING) that detects "this process's own binary file has been modified/replaced since the process started" — e.g. compare a hash or inode+mtime recorded at boot time against the current state of the same path — and distinguish this from a legitimate hot-reload (which re-execs into a *new process*, so the check only needs to catch the in-place-content-changed case a `cp` produces, where the process keeps running without re-exec). Surface it loudly: a `spawn_path.modified_in_place` telemetry event and a `needle doctor` warning naming the affected workers. This doesn't stop an operator from running `cp`, but it stops the failure from being silent — both historical incidents were confusing specifically because nothing said "your spawn-path binary just changed under you."
4. **Document `needle upgrade` as the only sanctioned path for a manual/single-host update, with the reasoning visible at the call site** — add a one-line note to `needle upgrade --help` and to the top of `docs/plan/plan.md`'s Binary Structure section stating plainly that `cp`/`mv` onto `~/.local/bin/needle` or `~/.needle/bin/needle-stable` while any worker is running is unsupported and will either disrupt live sessions (content overwrite) or permanently stall hot-reload until 11.1 ships (rename/unlink) — not just documented in an ADR an operator has to already know to look for.
5. **Ship through the existing release path**: version bump, needle-ci (fmt + clippy + test on iad-ci), GitHub Release, staged canary rollout (`:testing` → `:stable`) — per plan.md's established Deployment convention. 11.1 in particular should be validated with its own canary fixture (kill a running worker's spawn-path inode via `mv` in a test harness, confirm it self-heals within one cycle) before promotion to `:stable`, since it is itself part of the hot-reload machinery it's patching.

## Consequences

- 11.1 fixes the more severe of the two incidents (permanent silent stall) with a small, contained change to one error-handling branch — no new mechanism, just correct handling of a case that was previously treated as "log and ignore."
- 11.2 means `needle upgrade` gains a canary-validation step it didn't have before — slightly slower (a canary run instead of an immediate swap), and now depends on the canary fixtures being adequate for a full release diff, the same open risk Phase 9's Consequences already flag. Both phases should share validation work here rather than duplicate it if built close together.
- 11.3 cannot prevent an operator from directly overwriting a binary file — Unix file permissions don't distinguish "the sanctioned upgrade tool" from "any process with write access." It converts a silent failure into a visible one, which is the achievable bar here, not full prevention.
- None of 11.1-11.3 change the `cp` incident's actual disruption (a content-changed spawn-path file legitimately looks like a real hot-reload signal, and workers correctly re-exec on it) — that incident's fix is entirely 11.2 + 11.4 (route deploys through `:testing`/canary and document why direct writes are unsupported), not a hot-reload code change.
