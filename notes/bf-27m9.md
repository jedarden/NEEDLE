# Analysis: `repeat_interval_skips_max_depth_beads` Test

## Test Location
`src/mitosis/mod.rs:1203-1244`

## Test Purpose

This test verifies that **mitosis child beads are excluded from repeat interval re-evaluation**, preventing infinite recursion in the bead splitting mechanism.

## Key Concepts

### Mitosis
Mitosis is the process of splitting a failed multi-task bead into focused child beads. When a bead fails repeatedly, the system dispatches an AI agent to analyze whether the bead contains multiple independent tasks. If so, it creates child beads for each subtask.

### repeat_interval
When `repeat_interval > 0`, mitosis fires at specific failure count intervals:
- `failure_count == 1` (first failure)
- `failure_count == 1 + N` (first repeat tick)
- `failure_count == 1 + 2N` (second repeat tick)
- etc.

For example, with `repeat_interval: 50`:
- Triggers at: 1, 51, 101, 151, ...
- Does NOT trigger at: 2-50, 52-100, 102-150, ...

### mitosis-depth Label
When a child bead is created via mitosis, it receives labels:
- `mitosis-child` - marks the bead as a mitosis product
- `mitosis-depth:1` - indicates this is a first-generation child (depth = 1)
- `parent-<parent_id>` - tracks lineage for deduplication

## What the Test Verifies

**The test confirms that child beads (with `mitosis-depth:1`) are skipped during repeat interval evaluation**, even when their failure_count would normally trigger mitosis.

### Test Setup

// Config: repeat_interval = 50

### Expected Behavior
The test asserts that the evaluation returns `MitosisResult::Skipped`, confirming that the mitosis-depth label prevents re-evaluation.

## Core Logic (src/mitosis/mod.rs:124-134)

```rust
let should_fire = if self.config.repeat_interval > 0 {
    // repeat_interval mode: fire at 1, 1+N, 1+2N, ...
    // But skip beads that are already mitosis children (have mitosis-depth label).
    let has_mitosis_depth_label =
        bead.labels.iter().any(|l| l.starts_with("mitosis-depth:"));
    let is_repeat_tick =
        failure_count > 1 && (failure_count - 1) % self.config.repeat_interval == 0;

    // Fire at first failure OR at repeat interval ticks (if not a mitosis child)
    failure_count == 1 || (is_repeat_tick && !has_mitosis_depth_label)
} else { ... };
```

**Key condition:**
```rust
failure_count == 1 || (is_repeat_tick && !has_mitosis_depth_label)
//                                      ^^^^^^^^^^^^^^^^^^^^^^^^
//                                      This prevents repeat mitosis on children
```

## Why This Matters

### Preventing Runaway Recursion

Without this check, the following scenario could occur:

1. Parent bead fails 51 times → mitosis splits it into children
2. Child beads get `mitosis-depth:1` label
3. Child bead fails 51 times → mitosis would split it again (grandchildren)
4. Grandchildren would get `mitosis-depth:2` label
5. This could continue indefinitely, creating exponentially many beads

The test verifies that step 3 is **blocked** - child beads are never re-evaluated for mitosis, regardless of their failure count.

### "Max Depth" Interpretation

The test name mentions "max depth beads" but the code currently checks for ANY `mitosis-depth:` label (depth 1, 2, etc.). This suggests:
- Current implementation: prevents ANY mitosis-depth bead from re-splitting
- Future enhancement: might support configurable max depth (e.g., depth < 3 can split again)
- The "max depth" terminology anticipates this enhancement

## Potential Failure Points

If this test were to fail, the likely causes would be:

1. **Label parsing bug**: The `starts_with("mitosis-depth:")` check fails to match the actual label format
2. **Logic inversion**: The `!has_mitosis_depth_label` condition is accidentally removed or inverted
3. **Repeat interval calculation**: The `(failure_count - 1) % repeat_interval == 0` formula is incorrect
4. **Integer overflow**: If failure_count exceeds u32::MAX (highly unlikely in practice)
